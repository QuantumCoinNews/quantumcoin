# HTTP request size limits

The canonical root API starts through `node.Runtime.ServeHTTP` with
`node.DefaultHTTPServerOptionsV1`. The retired `api.StartHTTP` fails closed and
does not create a second HTTP listener.

* Request bodies: 1 MiB (1,048,576 bytes). The outer HTTP guard rejects a known
  larger Content-Length before application dispatch. MaxBytesReader bounds
  consumed bytes for unknown-length/chunked requests. Signed transaction and
  miner-control parsers also apply this bound locally.
* Monitoring actions and publisher reports have a stricter 4,096-byte JSON body
  bound. The parser must consume one complete JSON document and the following
  whitespace/EOF before any state change. Limit errors from either decode are
  HTTP 413; ordinary malformed JSON remains HTTP 400.
* MaxHeaderBytes: explicitly 1 MiB. Go's HTTP/1 parser adds a bounded 4 KiB
  buffering allowance; this is not an exact application-field cutoff. A request
  exceeding the parser budget gets HTTP 431 before route dispatch. That response
  is generated by net/http and is not the API's JSON error envelope.
* Header read timeout: 5 seconds; request read/write timeouts: 15 seconds; idle
  timeout: 60 seconds. These are transport budgets, not consensus settings.

Body overflow detected by an application parser uses the canonical JSON error
envelope with HTTP 413. Earlier auth/CORS/method/rate rejection keeps its own
status: invalid or unauthorized traffic is not promised a body-size oracle.
Handlers that do not consume a body do not buffer it; unknown-length excess on
such a rejected request need not be parsed merely to return 413.

The Windows closing-connection compatibility wrapper drains only explicitly
sized allowed bodies, up to 1 MiB and 200 ms. It does not drain unknown-length,
oversized, or Expect-handshake bodies. No unlimited body buffering, body replay,
or consensus/economy change is part of this contract.
